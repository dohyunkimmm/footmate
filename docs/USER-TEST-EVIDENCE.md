# FootMate 과업 기반 사용자 검증 근거

이 문서는 PBL 교육 시점부터 현재까지 FootMate를 고도화하며 진행한 **소규모 과업 기반 사용성 검증(Task-based Usability Test)**의 범위와 해석 한계를 정리합니다.

이 검증은 사용자가 서비스를 자유롭게 이용했을 때의 전환율이나 재이용률을 측정한 실험이 아닙니다. 특정 동선에서 버그·막힘·상태 복구 문제를 찾기 위해 **구체적인 행동 과업을 지정하고 해당 동선을 수행하도록 요청한 검증**입니다.

## 1. 참여자 구성

- 참여자: **6명**
- 기기 OS: **iOS 4명 / Android 2명**
- 성별: **여성 5명 / 남성 1명**
- 풋살 숙련도: **입문 2명 / 초급 2명 / 중급 1명 / 고급 1명**
- 포지션 과업: **수비수 2명 / 공격수 2명 / 미드필더 2명**

숙련도 구성은 풋살에 익숙하지 않은 5명에게 입문 2명·초급 2명·중급 1명의 조건을 요청하고, 풋살에 익숙한 1명에게 고급 조건을 요청한 결과입니다.

성별·숙련도·포지션 구성은 시장 대표 표본을 의미하지 않습니다. 성별은 원본 참여자 구성 정보로만 기록하며, 현재 관찰 결과를 성별 차이로 해석하거나 설계 판단의 근거로 사용하지 않습니다. 현재 목적은 다양한 조건과 기기에서 핵심 동선이 정상적으로 이어지는지 확인하는 것입니다.

## 2. 행동 과업

가입 관련 과업은 다음처럼 요청했습니다.

| 과업 | 요청 횟수 |
| --- | ---: |
| 회원가입 전까지 탐색 | 2회 |
| Kakao로 회원가입까지 | 2회 |
| Google로 회원가입까지 | 2회 |
| 일반 이메일로 회원가입까지 | 2회 |
| **합계** | **8회** |

참여자는 6명이고 가입 관련 과업은 총 8회이므로, **일부 참여자가 복수 과업을 수행한 검증**입니다. 현재 개인별 참여자-과업 매핑은 확정된 기록으로 남아 있지 않으므로 임의로 1인 1과업처럼 재구성하지 않습니다.

## 3. 검증 방식

단순히 “앱을 써보고 불편한 점을 알려 달라”고 요청하지 않고, 확인하려는 동선에 맞춰 행동을 지정했습니다.

예시는 다음과 같습니다.

- 회원가입하지 않은 상태에서 자신의 수준·포지션에 맞는 경기를 탐색하고 상세까지 이동
- 참가 의도가 생긴 상태에서 Kakao 로그인을 선택하고 가입 완료까지 진행
- 같은 참가 맥락에서 Google 로그인을 선택하고 인증 후 원래 동선으로 복귀
- 일반 이메일 가입을 진행하고 가입·인증·로그인 단계의 상태 변화를 확인

이 방식의 목적은 **어느 화면에서 무엇을 하다가 문제가 발생했는지 재현 가능한 동선으로 남기는 것**입니다.

## 4. 과업별 관찰 단위와 증거 수준

현재 남아 있는 기록만으로도 과업과 관찰 단위를 구분할 수 있지만, 개별 참여자별 버그 목록이나 발견 시점까지 모두 복원할 수 있는 수준의 원본 기록은 아닙니다. 따라서 아래 표는 **무엇을 확인한 검증인지 설명하는 관찰 프레임**이며, 실제로 발견된 버그 개수를 새로 만들어낸 목록이 아닙니다.

| 과업 | 관찰 단위 | 현재 증거 수준 |
| --- | --- | --- |
| 회원가입 전 탐색 | 조건 선택 → 추천/목록 → 상세 이동, 가입 전에도 탐색 흐름이 이어지는지 확인 | 과업 수행 횟수는 확인됨. 참여자별 상세 이슈 기록은 미확정 |
| Kakao 가입 | 참가 맥락 → Kakao 인증 → 가입 완료, 인증 뒤 원래 흐름으로 복귀하는지 확인 | 과업 수행 횟수는 확인됨. 개별 오류의 발생 순서·빈도는 미확정 |
| Google 가입 | 참가 맥락 → Google 인증 → 원래 동선 복귀, 이전 선택 상태와 복귀 위치 확인 | 과업 수행 횟수는 확인됨. 개별 오류의 발생 순서·빈도는 미확정 |
| 이메일 가입 | 가입 → 인증 → 로그인 단계의 상태 변화와 재진입 흐름 확인 | 과업 수행 횟수는 확인됨. 참여자별 상세 이슈 기록은 미확정 |

공통 관찰 항목은 인증 방식, 이전 선택 상태, 복귀 위치, 중복 행동, 모바일 브라우저 차이처럼 **동선에 종속된 상태 변화**입니다. 이후 개별 이슈를 추가할 때는 `Task → Observation → Issue → Decision → Fix → Re-test` 순서로 기록하고, 원본 근거가 없는 칸은 추정으로 채우지 않습니다.

## 5. V1 → V2 고도화 증거 흐름

FootMate의 발전 과정은 기능 개수보다 **검증 범위가 어떻게 넓어졌는지**로 정리합니다.

| 단계 | 확인 가능한 변화 | 증거 성격 |
| --- | --- | --- |
| PBL V1 | 문제 가설, Persona/JTBD, 핵심 탐색·참가 흐름을 프로토타입으로 구체화 | 설계 가설·초기 구현 |
| 과업 기반 사용자 검증 | 6명에게 iOS·Android에서 탐색·가입 과업을 요청하고 총 8회의 가입 관련 과업을 수행 | Usability Evidence |
| 제품 고도화 | Guest First 탐색, 인증, 참가·취소, 계정 복구, 체크인·대기열·알림 등 실제 서비스 상태와 예외 처리를 확장 | 기능·운영 정책·상태 계약 |
| Production QA | 자동 Regression, Browser E2E, 접근성, Visual Regression, Mobile Safari/WebKit, Production Smoke로 배포 상태를 검증 | QA / Release Evidence |
| 측정 준비 | 상세 진입, 참가 전환, 실패·복구, 체크인, 재탐색, AI 사용률의 분자·분모와 관찰 기준을 정의 | Validation Metric 설계 |

이 순서는 **사용자 검증이 모든 후속 기능을 직접 발생시켰다는 인과 주장**이 아닙니다. 과업 기반 사용자 검증, 제품 구현, 운영 정책, 자동 QA를 서로 다른 근거로 쌓아 V1보다 검증 가능한 범위를 넓혀 온 과정입니다.

## 6. 현재까지의 학습

가장 명확한 학습은 다음과 같습니다.

> 구체적인 행동을 지정해야 해당 동선에서 발생하는 버그를 찾을 수 있다.

서비스 전체를 자유롭게 탐색하도록 두면 사용자가 문제 구간을 지나가지 않을 수 있습니다. 반대로 확인할 행동을 명시하면 인증 방식, 이전 선택 상태, 복귀 위치, 중복 행동, 모바일 브라우저 차이처럼 **동선에 종속된 오류를 발견하고 같은 조건으로 재검증하기 쉬워집니다.**

따라서 FootMate의 사용자 검증은 다음 반복 구조로 정리합니다.

**가설 → 행동 과업 지정 → 행동 관찰 → 버그·막힘 확인 → 수정 → 동일 동선 재검증**

## 7. 포트폴리오 해석 경계

이 검증으로 말할 수 있는 것은 다음입니다.

- PBL 교육 이후 실제 사용자 6명을 대상으로 iOS·Android에서 과업 기반 동선 검증을 진행함
- 풋살 숙련도와 포지션 조건을 나눠 탐색·가입 동선을 확인함
- 회원가입 전 탐색, Kakao, Google, 이메일 가입을 포함한 총 8회의 가입 관련 과업을 요청함
- 구체 행동 과업을 통해 동선별 버그·막힘을 찾고 고도화하는 방식으로 검증함
- PBL V1 이후 사용자 검증, 제품 고도화, Production QA, 측정 준비까지 검증 범위를 단계적으로 확장함

이 검증만으로 말할 수 없는 것은 다음입니다.

- 전환율이 개선되었다는 정량 성과
- 특정 가입 방식의 선호도 우위
- 성별에 따른 행동 차이 또는 선호 차이
- 전체 풋살 이용자를 대표하는 사용자 인사이트
- 시장 적합성이나 재이용 효과
- 사용자 검증 하나가 모든 후속 기능 변경의 직접 원인이었다는 인과 관계

제품 KPI의 `Measured Result`는 별도 기준입니다. 실제 무료 Beta 이용자 cohort를 운영·테스트·자동 QA와 구분하고 관찰 기간·분자·분모를 고정한 뒤 Baseline부터 측정합니다. 세부 기준은 [`BETA-MEASUREMENT-READINESS.md`](./BETA-MEASUREMENT-READINESS.md)와 [`SERVICE-PLANNING-EVIDENCE.md`](./SERVICE-PLANNING-EVIDENCE.md)를 따릅니다.
