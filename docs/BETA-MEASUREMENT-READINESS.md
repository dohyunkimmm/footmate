# FootMate Beta 측정 준비 기준

이 문서는 FootMate의 **Validation Metric을 실제 Measured Result로 전환하기 위한 계측·표본·판정 기준**을 정리합니다. 숫자를 채우기 위한 문서가 아니라, 어떤 데이터만 사용자 성과로 인정할지 먼저 고정하는 문서입니다.

현재 Case Study의 KPI는 모두 **Validation Metric**이며 아직 **Measured Result가 아닙니다**. 운영·테스트 계정, 자동 QA, `/demo` sample/simulation을 실제 Beta 성과에 섞지 않습니다.

## 1. Measured Result 인정 조건

Measured Result는 아래 조건을 모두 만족할 때만 공개합니다.

- **대상 구분** — 실제 무료 Beta 이용자와 운영·테스트 계정을 구분할 수 있어야 합니다.
- **관찰 기간** — 시작일·종료일과 지표별 관찰 완료 조건을 함께 기록합니다.
- **표본 크기** — 분자·분모와 유효 표본 수를 함께 기록합니다.
- **중복 제거** — 동일 사용자·경기·탐색·참가 흐름의 재시도를 정의된 단위로 중복 제거합니다.
- **누락 확인** — 이벤트 누락이나 관찰 미완료 표본을 별도로 기록합니다.
- **정의 고정** — 비교 전후에 같은 분자·분모·제외 기준을 사용합니다.

첫 측정값은 **개선 성과가 아니라 Baseline**으로 기록합니다. 이후 한 번에 하나의 가설을 변경하고 같은 정의로 재측정한 뒤에만 변화량을 비교합니다.

## 2. 현재 계측 준비 상태

현재 Supabase에는 인증·경기·참가·체크인 기록과, 명시적 동의 이후 실제 경기 탐색 이벤트를 전송하는 기능이 연결되어 있습니다. 운영자가 `discovery_cohorts`에서 실제 Beta 이용자를 `pilot`으로 지정하고 테스트·미분류·운영 계정을 집계에서 제외하는 기준도 구현되었습니다. 다만 유효한 실제 이용자 표본·관찰 기간·지표별 분자/분모와 누락 검증이 아직 확정되지 않아, 저장된 기록을 사용자 성과로 집계하거나 KPI를 Measured Result로 공개하지 않습니다.

| Validation Metric | 현재 활용 가능한 근거 | Measured Result 전 필요한 조건 | 현재 상태 |
| --- | --- | --- | --- |
| Match Search → Detail CTR | 경기·참가 상태와 별도로 탐색 UI 존재 | 검색 결과 노출·상세 진입 이벤트, 탐색 세션 ID, cohort 구분 | **미측정** |
| Detail → Join Conversion | `participations`의 참가 완료 상태 | 상세 조회 이벤트, 사용자·경기 기준 24시간 관찰, cohort 구분 | **미측정** |
| Zero Result Rate | 실제 경기 데이터와 AI/rules 탐색 경로 | 검색 요청·정상 처리·결과 수 이벤트, 중복 요청 기준 | **미측정** |
| Join Failure Rate | 참가 상태·운영 이벤트 | 참가 시도 flow ID, 실패·취소·timeout 후 최종 상태 구분 | **미측정** |
| Recovery Success Rate | 참가·취소·체크인 복구 경로 | 실패 flow와 복구 완료를 같은 flow ID로 연결 | **미측정** |
| Check-in Completion Rate | `participations.checked_in_at`, 경기 상태 | 종료 경기·확정 참가자 cohort 구분, 취소 제외 규칙 적용 | **Baseline 준비** |
| Repeat Match Search Rate | 참가·경기 완료 상태 | 경기 후 탐색 이벤트, 사용자별 7일 관찰 완료 여부 | **미측정** |
| AI Search Adoption Rate | AI connected / rules-fallback 탐색 경로 | 탐색 세션별 AI 진입점 노출·요청 이벤트, fallback 분리 | **미측정** |

`Baseline 준비`는 계산 가능한 상태 데이터가 있다는 뜻이며, 실제 사용자 cohort가 검증되기 전에는 결과값을 공개하지 않습니다.

## 3. 측정 기록 형식

실제 Beta 측정을 시작하면 지표마다 아래 항목을 함께 남깁니다.

| 항목 | 기록 내용 |
| --- | --- |
| 기간 | YYYY-MM-DD ~ YYYY-MM-DD |
| 대상 | 실제 무료 Beta 이용자 |
| 제외 | 운영자·테스트·자동 QA·sample/simulation |
| 분자 / 분모 | 정의된 집계 단위의 실제 건수 |
| 결과 | 비율 또는 N/A |
| 유효 표본 | 관찰 조건을 완료한 사용자·세션·흐름 수 |
| 데이터 누락 | 누락·관찰 미완료 건수와 이유 |
| 해석 | 공급 부족·정책·인증·추천 등 다른 원인과 분리한 해석 |
| 다음 변경 | 한 번에 하나의 가설만 변경 |

분모가 0이면 `0%`가 아니라 `N/A`로 기록합니다. 낮은 표본에서 나온 변화는 사용자 가치가 입증된 성과처럼 표현하지 않습니다.

## 4. 첫 Beta 측정 순서

1. 실제 Beta 이용자를 측정 가능한 cohort로 구분합니다.
2. 검색 결과 노출·상세 진입·검색 결과 수·AI 검색 요청에 최소 이벤트 계약을 정의합니다.
3. 참가·복구 이벤트에 동일 flow ID를 연결해 재시도 중복을 제거합니다.
4. 관찰 기간과 표본 수를 먼저 기록하고 8개 지표의 Baseline을 계산합니다.
5. 이탈이 가장 큰 한 구간을 선택해 원인을 분류합니다.
6. 한 가지 요구사항·정책·UI만 변경하고 같은 정의로 재측정합니다.
7. `가설 → 관찰 → 변경 → 재검증`을 Case Study의 Measured Result로 반영합니다.

## 5. 포트폴리오 표기 원칙

- 실제 측정 전: **Validation Metric / Baseline 미측정**
- 첫 유효 측정 후: **Measured Baseline** + 기간·표본·분자·분모
- 동일 정의의 재측정 후: **Observed Change** + 변경 내용과 한계
- 충분한 표본·비교 설계가 없으면 인과적 표현인 “개선했다”, “증가시켰다”를 사용하지 않습니다.

세부 KPI의 분자·분모·관찰 기준은 [`SERVICE-PLANNING-EVIDENCE.md`](./SERVICE-PLANNING-EVIDENCE.md)를 기준으로 유지합니다.


## 탐색 계측 구현 보완 · 2026-10-27
필터 적용·추천 요청/완료·카드 노출·다시 추천·상세 진입과 참가 이벤트를 탭의 탐색 ID로 연결해 sessionStorage에 최대 200개 보관합니다. 탐색 채널은 `footmate:beta:discovery-measurement`입니다. Demo는 source/cohort를 demo로, Beta는 cohort를 unclassified로 유지합니다. 이메일·인증 토큰·지역 조건 원문은 수집하지 않습니다.
로그인 사용자가 MY/설정의 「추천 개선 통계 참여」에서 명시적으로 동의한 이후의 실제 경기 이벤트만 Supabase discovery_events로 전송합니다. 데모·게스트·동의 이전 기록은 전송하지 않습니다. 참여 해제는 해당 계정의 서버 탐색 기록을 삭제합니다. 이벤트 전송 성공 후 대기열을 최대 10개씩 비우며, 전송 실패는 추천·참가를 막지 않고 후속 이벤트에서만 재시도합니다. 통계 해제 요청 실패 시 이 기기의 수집을 중지하고 계정별 로컬 해제 요청을 저장합니다. 새로고침·재로그인 시 서버 해제를 재시도하며 서버 확인 전에는 다시 활성화하지 않습니다. UI는 서버 기록 삭제 미확인과 재시도 버튼을 표시합니다. 다른 기기의 수집 중지와 서버 기록 삭제는 서버 해제 요청이 성공해야 확정됩니다.

운영자 콘솔의 「추천 탐색 지표」는 운영자 MFA(AAL2) 확인 후 기존 RPC `operator_discovery_metrics`에서 **최근 7일**의 이벤트별 고유 세션·이용자·건수를 조회합니다. 별도 RPC `operator_discovery_kpi_baseline`은 화면에서 `p_since`를 명시해 **최근 21일**의 파일럿 전환 기준선 4종을 조회합니다(아래 참고). 운영자가 `discovery_cohorts`에서 `pilot`으로 지정하고 통계 전송에 동의한 실제 이용자만 포함하며 test·미분류·운영자·데모는 제외합니다. 클라이언트에는 cohort 쓰기 권한이 없습니다. 실제 pilot 0명이므로 기준선은 N/A이며 사용자 전환 성과가 검증된 것은 아닙니다.

첫 화면 비교 진입: /beta?opening=control (소개 후 선택), /beta?opening=quick (바로 조건 선택), /beta?opening=compare (탭별 별도 실험 키로 무작위 고정). /demo에서도 같은 경로를 체험할 수 있으나 데모 기록은 서버 집계에서 제외됩니다. 기본 진입 동작은 유지합니다. 새 탭·새 브라우저 세션에서 첫 방문 조건으로 비교하고 일반 진입은 기존 entered 세션에서 소개를 반복하지 않습니다. 명시적인 compare 진입은 배정된 소개/바로 선택 화면을 다시 보여 주어 배정과 실제 화면이 어긋나지 않게 합니다. 일반 방문과 수동 control/quick 진입은 비교 실험 배정 키를 덮어쓰지 않습니다. 이벤트 종류별 합계는 사용자 전환율이나 인과적 성과가 아니며 동일 표본의 순서·기간을 정의한 후 별도 분석해야 합니다. 익명 방문자의 이탈과 동의 전 첫 화면은 측정하지 않습니다.

추천 조정: 상세 화면의 관심/다른 시간/다른 구장 선택을 계정·데모별 브라우저에 최대 50개 저장하고 30일간 사용합니다. 기한이 지난 반응은 추천에서 제외하며 초기화 버튼은 저장 기록을 삭제합니다. 실제 경기 후 재참가 의향도 읽어 추천 순서를 조정합니다. 개인화는 기존 AI/규칙 후보의 순서에만 제한적으로 작용하고 필터·정원·날짜 범위를 확장하지 않습니다.


## 저장 공간·계정 갱신 QA 보완
통계 전송은 서버 동의와 이 브라우저의 명시적인 참여 허용 기록이 모두 있어야 활성화합니다. 기존 서버 동의만 있고 브라우저 허용 기록이 없는 경우 자동 수집하지 않으며, 설정에서 이 브라우저 참여 또는 서버 참여 해제를 선택할 수 있습니다. 참여 시 같은 길이의 허용/해제 상태를 기록할 공간을 확보합니다. 해제 상태 쓰기가 실패하면 기존 허용 기록을 제거하고, 허용 기록이 없으면 재로그인·새로고침 뒤에도 수집하지 않습니다. 서버 기록 삭제는 서버 응답 성공 후 확정됩니다.
같은 계정·백엔드의 상태/토큰 갱신은 대기열을 보존하고 새 인증 정보로 전송합니다. 로그아웃·계정 변경·동의 변경에서는 수집 세대를 교체하고 이전 대기열을 폐기합니다. 메모리 대기열은 최대 50개이며 전송 실패와 페이지 종료에 따른 전송 보장은 하지 않습니다. Chromium 및 Mobile Safari에서 해제 실패·저장 공간 부족·새로고침·복구·재참여 흐름을 검사합니다.

## 2026-10-30 · 파일럿 KPI 기준선·추천 조건 동기화 적용 경계

- [PR #727](https://github.com/dohyunkimmm/footmate/pull/727)의 Supabase 운영 migration `20261030032856_beta_preferences_pilot_metrics` 적용으로 `public.operator_discovery_kpi_baseline(p_since timestamptz)` 및 `public.beta_user_preferences`가 생성됐습니다. 파일럿 기준선과 기존 이벤트 집계는 **서로 다른 RPC/관찰 기간**입니다. 접근은 운영자 membership과 실제 MFA AAL2가 필요하지만, **실제 Auth 서명 JWT를 이용한 실계정 수동 검증은 아직 미완료**입니다([#611](https://github.com/dohyunkimmm/footmate/issues/611)).
- 기준선 4종: `search_to_detail`(추천 노출→상세 열기), `zero_result`(완료된 추천 중 0건), `detail_to_join`(경기 상세→24시간 내 참가 완료), `repeat_search_7d`(체크인한 완료 경기 뒤 7일 이내 재탐색). 각 결과는 분자/분모/유효 사용자/백분율을 분리하며, **지표별 유효 사용자 또는 분모 5 미만**이면 해당 값은 N/A로 비공개 처리합니다. 표본 억제는 결괏값 0과 다릅니다.
- 현재 `pilot` 지정 계정은 **0명(2026-10-30 운영 DB 조회)**입니다. 신규 KPI 함수가 실행되고 QA를 통과했다는 사실은 효과·실사용 전환율 개선에 대한 증거가 아닙니다. 사용자를 자동 분류하거나 데모·모의 데이터를 전환율 분모에 섞지 않습니다.
- 인증된 사용자 추천 조건(활동 지역·실력·포지션·날짜/시간 등)은 `beta_user_preferences`의 계정별 RLS 정책으로 서버에 보관·기기 간 복구할 수 있으며, 네트워크 장애 시 로컬 저장으로 대체합니다. **추천 조건 동기화는 탐색 이벤트 수집 동의와 별도의 기능**이고, 데모/게스트 조건과 브라우저에 저장된 추천 반응·순서·참가 시뮬레이션을 전부 동기화하는 기능은 아닙니다.
