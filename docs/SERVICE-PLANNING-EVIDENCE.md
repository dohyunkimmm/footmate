# FootMate 서비스 기획 근거

이 문서는 현재 Case Study의 역할·문제 가설·우선순위·성공 지표·검증 한계를 설명합니다. 제품 기능 추가나 실제 사용자 성과 보고서가 아닙니다. 근거는 현재 README, 구현 파일, 테스트, Beta 운영 절차와 과업 기반 사용자 검증 기록입니다.

## 역할과 책임 범위

- Role: IT Service Planner / Product Planner 관점의 프로젝트
- Scope: 문제 정의, 설계용 Persona/JTBD, IA와 Service Flow, 기능·운영 정책, 과업 기반 사용성 검증, API/Data contract, Interactive Prototype, QA scenario, Release verification
- Responsibility: 요구사항 우선순위와 예외 처리 기준을 설명하고, 실제 연동·시뮬레이션·미연동을 구분

현재 저장소는 설계·구현·테스트 산출물의 근거입니다. 실제 조직에서의 직위, 타인과의 협업 실적, 개인별 구현 기여율을 입증하는 자료로 확대 해석하지 않습니다. AI 보조 작업과 사람 검수를 구분하며, 기여율이나 팀 규모를 임의로 수치화하지 않습니다.

| 협의 대상 | 전달할 기준 | 현재 산출물 근거 |
| --- | --- | --- |
| 개발 | 입력·출력, 권한, 정원 동시성, 오류·재시도, 상태 소유권 | `src/v5/domain/`, `src/v5/infrastructure/`, `supabase/migrations/` |
| 디자인 | IA, 정상·로딩·빈 결과·오류·복구 화면, CTA 우선순위 | Case Study, `/app`, `/beta`, Browser E2E |
| 운영 | 취소 마감, 포지션 정원, 대기열, 체크인, 알림 실패·복구 | `/beta/operator`, `docs/BETA-PILOT-RUNBOOK.md` |

이는 협의 가능한 수준의 정의와 산출물이며 실제 다인 협업 기록이나 합의 성과가 아닙니다.

## 문제 → 서비스 목표 → 요구사항

| 문제 가설 | 서비스 목표 | 요구사항 | 검증 지표 |
| --- | --- | --- | --- |
| 조건을 따로 확인하면 탐색 부담과 이탈 가능성이 커짐 | 적합한 경기의 상세까지 진행 | 조건 해석, 필터, 추천 이유, 결과 없음 복구 | 상세 진입률, 결과 없음 비율 |
| 추천 근거·자리·취소 규칙이 불명확하면 참가를 망설임 | 판단 근거를 이해한 뒤 참가 | 상세 정보 순서, 참가 직전 인증, 정원·취소 정책 | 상세→참가 전환율, 참가 실패율 |
| 참가 후 다음 행동이 흩어지면 참석·재이용 기회를 잃음 | 경기 참여와 다음 탐색 연결 | 체크인, 알림, 경기 후 피드백, 재탐색 | 체크인 완료율, 7일 내 재탐색률 |

Why now는 시장 성장 주장 대신 프로젝트의 현재 검증 과제로 설명합니다. 자연어 탐색이 추가된 시점에 편의성뿐 아니라 추천 사실의 신뢰성, 참가 안전성, 운영 복구를 함께 확인해야 합니다. 수익화는 무료 Beta 이후의 검증 범위이며 매출·수익성·시장 적합성을 입증하지 않았습니다.

Persona의 평일 저녁·주 1~2회·30분 안쪽 이동은 설계 가정입니다. 실제 인터뷰로 검증한 대표 사용자 집단이나 이용 통계가 아닙니다. 다만 PBL V1 이후 약 6명을 대상으로 iOS·Android, 숙련도·포지션, 회원가입 전·Kakao·Google·이메일 가입 동선을 나눠 **과업 기반 사용성 검증**을 진행했습니다. 이 검증은 Persona의 대표성을 입증하는 조사가 아니라 동선별 버그·막힘·상태 복귀를 확인하기 위한 검증이며, 상세 범위와 해석 한계는 [`USER-TEST-EVIDENCE.md`](./USER-TEST-EVIDENCE.md)에 기록합니다.

## 대안과 선택 이유

목록·필터, 지도, 커뮤니티를 해결 방식의 대안으로 비교합니다. 특정 업체의 최신 기능이나 시장 점유율을 조사한 경쟁 분석은 아닙니다.

| 대안 | 확인할 수 있는 가치 | FootMate에서 검증할 차이 |
| --- | --- | --- |
| 목록·필터 탐색 | 여러 후보의 조건 비교 | 조건 해석과 추천 이유가 판단 부담을 줄이는가 |
| 지도 탐색 | 위치와 이동 범위 파악 | 위치 이외의 레벨·포지션·정원을 함께 판단할 수 있는가 |
| 커뮤니티 탐색 | 경험·맥락 정보 확인 | 참가·운영 상태를 구조화해 다음 행동으로 연결할 수 있는가 |

## 우선순위와 Trade-off

우선순위는 사용자 판단 가치, 참가 실패 영향, 검증 가능성으로 설명합니다. 현재 범위의 판단 근거를 정리한 것이며 과거 정량 점수나 회의 기록을 새로 만들어낸 것은 아닙니다.

| Decision | Reason | Trade-off | 근거 |
| --- | --- | --- | --- |
| 가입 전 추천·상세 공개 | 참가 전에 추천 가치를 판단 | 계정 기반 개인화·기기 간 연속성은 인증 이후 | `/app` guest-first flow |
| 무료 Beta의 참가·취소·체크인 우선 | 거래 안전성과 핵심 흐름을 먼저 검증 | 실제 PG와 수익화 검증 유보 | `/beta`, README |
| AI는 조건 해석, 추천 엔진은 순위 소유 | 경기 사실 생성과 근거 없는 순위 변경 방지 | 자유로운 생성·자동화 범위 제한 | `api/ai-match-assistant.js`, 추천 계약 |
| 참가 확정은 HITL | 의도하지 않은 상태 변경 방지 | 사용자의 확인 단계 필요 | 참가 계약·UI |
| 실패 시 rules fallback | 외부 AI 장애에도 탐색 지속 | 자연어 해석 범위가 제한될 수 있음 | AI fallback 계약 |
| Realtime 후 서버 상태 재조회 | 정원·참가 상태의 일관성 | 추가 요청과 조회 지연 | Beta infrastructure·growth |
| 알림과 참가 상태 분리 | 알림 전달 실패가 참가 사실을 덮어쓰지 않게 함 | outbox·재시도·전달 상태 운영 필요 | 이메일·Push outbox 계약 |

## Success Metrics — 측정 설계

아래 8개는 **Validation Metric**입니다. **Measured Result가 아니며**, 현재 기준값·KPI 측정용 실제 무료 Beta cohort·목표 수치는 제시하지 않습니다. 외부 분석 도구는 미연동입니다. 기존 이벤트·DB 상태가 있다는 이유만으로 아래 모든 지표가 이미 수집·집계된다고 주장하지 않습니다. 위의 과업 기반 사용자 검증 표본은 동선·사용성 검증 근거이며 이 KPI의 분자·분모에 포함하지 않습니다.

측정 대상은 실제 무료 Beta 이용자입니다. 운영·테스트 계정, 자동 QA, `/app` 샘플·시뮬레이션은 제외합니다. 탐색 세션은 30분 비활동 시 종료하는 측정 제안이며 현재 구현 계약이 아닙니다. 분모가 0이면 0% 대신 N/A로 기록합니다. 실패·재시도는 동일 흐름 ID로 중복 제거하도록 계측을 먼저 정의해야 합니다.

| 지표 | 분자 / 분모 | 관찰·판정 기준 |
| --- | --- | --- |
| Match Search → Detail CTR | 결과에서 상세로 이동한 세션 / 검색 결과가 1개 이상 노출된 세션 | 같은 탐색 세션, 세션당 1회 집계 |
| Detail → Join Conversion | 상세 조회 후 같은 경기에 참가 완료한 사용자·경기 쌍 / 상세 조회 사용자·경기 쌍 | 조회 후 24시간, 종료·마감 상태를 별도 분류; 24시간 관찰 완료 표본만 비교 |
| Zero Result Rate | 정상 처리 후 결과 0개인 검색 / 정상 처리된 검색 | 네트워크·서버 오류 제외, 동일 요청 중복 제거 |
| Join Failure Rate | 확정 실패 또는 미해결로 끝난 참가 흐름 / 참가 확정을 요청한 흐름 | 24시간 관찰 완료 흐름; 사용자 취소 별도 분류, timeout 후 상태 재조회로 결과 확인 |
| Recovery Success Rate | 같은 목적을 완료한 복구 흐름 / 재시도·상태조회로 복구 가능한 실패 흐름 | 24시간 이내; 마감처럼 원래 목적이 불가능한 상황의 대안 선택은 별도 지표 |
| Check-in Completion Rate | 체크인 완료 참가자·경기 쌍 / 취소되지 않은 종료 경기의 확정 참가자·경기 쌍 | 경기 종료 시점, 참가 취소 제외, 노쇼는 분모 유지 |
| Repeat Match Search Rate | 경기 후 7일 내 다시 탐색한 사용자 / 경기 후 7일 관찰이 완료된 참가 사용자 | 사용자당 첫 완료 경기를 기준으로 중복 제거; 탈퇴·관찰 누락 별도 기록 |
| AI Search Adoption Rate | AI 검색을 1회 이상 요청한 탐색 세션 / AI 검색 진입점이 노출된 탐색 세션 | connected-ai와 rules-fallback 결과를 별도 분류; 사용률을 품질로 해석하지 않음 |

참가 전환을 핵심 지표로 보되 실패율·복구율·체크인 완료를 함께 확인합니다. AI 사용률이 높아도 상세 진입이나 참가가 개선되지 않으면 성공으로 판단하지 않습니다. 결과 없음 비율은 공급 경기 수와 지역·시간의 영향을 받으므로 추천 품질만의 문제로 단정하지 않습니다.

## 데이터에 따른 다음 판단

아래는 향후 검증 규칙이며 관찰된 결과가 아닙니다.

- 결과 없음이 특정 지역·시간에 집중되면 공급 부족과 조건 해석 오류를 먼저 구분합니다.
- 상세 진입은 높고 참가가 낮으면 가격·시간·정원·인증·취소 규칙 중 이탈 구간을 확인합니다.
- 참가 완료는 유지되는데 체크인 완료가 낮으면 알림 전달, 시간 안내, 운영 예외를 확인합니다.
- AI 사용은 많지만 후속 전환이 낮으면 조건 추출 오류와 결과 적합성을 분리해 검토합니다.

처음에는 관찰 기간·표본 수·데이터 누락을 함께 보고 기준값을 확보합니다. 이후 한 번에 하나의 가설을 변경하고 비교하며, 낮은 표본의 변동을 인과적 성과로 표현하지 않습니다.

## QA와 회고

자동 QA는 구현 계약, 상태·복구, 접근성, 반응형, Visual Regression, Production Smoke를 검증합니다. 사람 검수는 실제 로그인·이메일 전달·Push 표시를 확인합니다. 과업 기반 사용자 검증은 지정 동선의 버그·막힘·상태 복귀를 관찰합니다. 어느 것도 사용자 만족이나 서비스 전환 개선의 대리 지표로 사용하지 않습니다.

설계에서 얻은 교훈은 연결 성공만으로 운영이 끝나지 않는다는 점입니다. 중복 요청, 정원 경합, 알림 전달 실패, 오래된 화면의 상태 갱신을 함께 정의해야 합니다. PBL V1 이후에는 약 6명에게 구체 행동 과업을 지정해 탐색·가입 동선을 반복 확인했고, 다음 단계의 자유 이용 Beta에서는 Persona 가정과 제품 KPI를 별도 cohort·Baseline으로 검증합니다. 실제 PG 도입은 핵심 흐름 검증과 별도의 운영·정산 판단이 필요합니다.
